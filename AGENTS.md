# Working with BuildSolid

This file guides agents working with the public BuildSolid tree. The Framework constitution defines BuildSolid's rules; this file provides navigation and working guidance.

## Read first

Read the material relevant to the task in this order:

1. [README](README.md) and this file.
2. [Framework overview](https://github.com/solimancifuentes/buildsolid/blob/v0.6.0/framework/README.md), [constitution](https://github.com/solimancifuentes/buildsolid/blob/v0.6.0/framework/docs/constitution.md), [context package](https://github.com/solimancifuentes/buildsolid/blob/v0.6.0/framework/docs/context-package.md) and [identity](https://github.com/solimancifuentes/buildsolid/blob/v0.6.0/framework/docs/brand/BUILD_SOLID_CANONICAL.md).
3. The applicable skill, template or example under [Project System](https://github.com/solimancifuentes/buildsolid/blob/v0.6.0/project-system/README.md).
4. [Contributing](CONTRIBUTING.md) or [Security](SECURITY.md) when the task concerns feedback or vulnerability reporting.

## Authority and scope

Framework defines the normative contract. Project System supplies compatible skills, templates and examples. Root documentation helps readers use that package and does not override Framework.

Accepted project knowledge lives in Git-tracked Markdown. Use the matching annotated version tag for a released contract; an untagged commit is a candidate. A proposal, issue, review or successful check does not authorize a later action.

Preserve the fourteen stages, three profiles, four modes, eighteen skills, twenty templates, artifact vocabulary and quality standards unless an accepted change explicitly changes them. Read the project's accepted intent, tasks and allowed effects before implementation. Update accepted artifacts in place and keep proposed decisions distinct from accepted ones.

## Working practice

Choose the applicable profile and mode. Start with a focused skill when its prerequisites are clear; use the orchestrator when work needs routing or coordination. Ask when a missing choice materially changes scope, authority or outcome. Carry out already authorized work without repeating settled questions.

Keep the workflow usable by one competent agent from a normal checkout. The three standalone helpers and executable examples are optional. They do not create an aggregate product CLI, required runtime, hosted service or authority to merge, publish or delete anything.

Verify actual behavior and the relevant changed surface before reporting completion. Record observed results and limitations in the project's accepted task and verification artifacts. Keep human control over consequential actions and follow the exact authority for each effect.

## Feedback and security

Use GitHub Issues for feedback. External code and content contributions are currently closed; follow [Contributing](CONTRIBUTING.md).

Report vulnerabilities through the private GitHub reporting interface described in [Security](SECURITY.md), never through a public Issue or pull request.
