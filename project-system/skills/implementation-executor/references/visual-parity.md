# Optional visual and interaction parity

Use this procedure only when an accepted task has a visual or interaction outcome that needs rendered proof. The accepted design or prior approved rendering supplies expected behavior; screenshots and browser observations are evidence, not a new source of intent. A normal single-agent checkout remains sufficient when a browser is available.

1. **Freeze the comparison before looking at the candidate.** Name the accepted baseline revision or artifact, tested implementation revision (including dirty state), route, viewport, zoom, color scheme, resolved fonts, data, user state and browser/OS. Name the meaningful states to cover: at least the changed default, expanded/interactive and error or empty state when applicable. Declare which layout differences are tolerable and why; avoid a tolerance that could hide missing, clipped or unreadable content.
2. **Capture and compare actual renders.** Take baseline and candidate screenshots at the same environment and state. Inspect content, hierarchy, spacing, clipping, contrast and responsive behavior relevant to acceptance. A pixel difference may be harmless font antialiasing; a missing message or displaced action is material even when a numeric score is small. Explain each material difference against the predeclared tolerance.
3. **Drive interactions.** Use mouse and keyboard to focus, activate, submit and recover as applicable. Inspect visible state, accessible names, labels, roles, focus order and state attributes such as `aria-expanded`. A static screenshot or API response cannot prove keyboard or accessibility behavior.
4. **Report the observed result.** Link actual captures and steps to the tested revision and environment. Mark each state passed, failed, unverified or inconclusive, including tool limits. If the browser cannot run, state visual/interaction coverage as unverified; do not infer a pass from HTML/CSS inspection alone.

When a comparison finds a defect, fix the candidate within accepted scope and recapture the affected states. Never replace or loosen the accepted baseline after seeing the failure merely to make the comparison pass. A changed design intent first needs the owning contract updated through its applicable acceptance. The [illustrative verification card fixture](../../../examples/execution-pilot/browser/README.md) has frozen healthy states and intentional negative controls; its defect variants demonstrate failures, not acceptable alternatives.
