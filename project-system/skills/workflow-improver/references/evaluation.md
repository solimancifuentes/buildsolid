# Bounded behavioral evaluation of guidance

Use this when a proposed workflow instruction needs evidence beyond a read-through. Before candidate runs, freeze the question, applicable safety and authority invariants, observable rubric, representative cases, known-bad sensitivity control, baseline and candidate instruction identities, model/effort/tools, environment, and a cost/time bound. Choose a sample that can reveal the specific predicted difference; do not select a passing threshold after seeing results. Record what is unavailable instead of estimating tokens or cost as fact.

For a **shared function**, both baseline and candidate can legitimately perform the task: give each the same accepted input in separate fresh contexts and equivalent environments. Avoid inherited implementation history or cross-contamination. Compare outputs against the predeclared rubric, with blinded review where feasible: reviewers see randomized labels and evidence rather than advertised version names. Include a known-bad control that should fail for a stated reason; if the method misses it, fix the method before drawing a quality conclusion.

For a **new capability**, use absolute acceptance against the candidate. A baseline that correctly refuses an unauthorized or unsupported new operation is not a quality failure. Negative controls still test boundaries. Review actual artifacts or behavior, not instruction presence, self-reported success, or a schema-only score. A rerun is justified by changed behavior, broken isolation, an insensitive control, or unresolved material dispute; unchanged independent cases need not be repeated.

Report per-case pass, fail, unverified, or inconclusive with evidence and input identities; distinguish reviewer judgment from observed command/render output. State sample size, contamination or tool limits, time/cost observations actually available, and which claim the data supports. One favorable case is not general superiority. Keep ordinary results in the current task/review record unless a durable decision or persistent issue needs its normal artifact. No new mandatory evaluation artifact, fixed trial count, model, or external service is implied.

Example (illustrative): compare two instructions for reviewing a reachable bug using identical code and an independently seeded false positive; both versions can review, so paired outputs and blind judgment are meaningful. When evaluating a newly added browser verification capability, judge the candidate's observed render and defect detection against absolute criteria; do not score the older version's honest “cannot verify” as a behavioral regression.
